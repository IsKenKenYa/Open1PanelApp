## 第一部分：代码架构优化（6 候选）

### ① 砍掉三层透传链 — tracer bullet：cronjob

**问题**：`CronjobService`(81 LOC) → `CronjobRepository`(86 LOC) → `CronjobV2Api`(192 LOC)，Service 的 `handleOnce/stop/delete/searchRecords/loadScriptOptions` 等 8/11 方法是 1:1 转发，depth≈0。

**做法**：cronjob 作为 tracer bullet，砍掉 Service 层，Provider 直持 Repository。
- 删除 `lib/features/cronjobs/services/cronjob_service.dart`
- `CronjobRepository` 已有 `_ensureApi()` 缓存 + 加工（response.data 兜底），是深 module，保留
- `CronjobService.searchCronjobs` 里的"加载 nextHandle 预览"加工逻辑下沉到 Repository（`searchCronjobsWithPreview`），注入 `GroupService` 依赖
- 3 个 Provider（`cronjobs_provider`/`cronjob_records_provider`/`cronjob_form_provider`）改为持有 `CronjobRepository`
- 验证：`flutter test test/` 下 cronjob 相关测试全绿；`flutter analyze` 无新增 warning

**范围控制**：本轮只做 cronjob 一条链，验证模式后再推广到 files/website/settings/firewall（A 类纯缓存 Repository）。深 module（Monitor 667 LOC / Database 386 / HostAsset / Group / Dashboard）一律不动。

### ② Settings 模块 DTO 泄漏修复

**问题**：`settings_service.dart:141,178,189` 的 interface 透出 `api.SnapshotSearch/ProxyUpdate/SettingUpdate`，`settings_provider.dart:4` 跨层 import API 层。

**做法**：Service interface 收窄为业务语义方法，DTO 构造藏进实现。
- `searchSnapshots(api.SnapshotSearch request)` → `searchSnapshots({String? name})`（内部构造 DTO）
- `updateProxySettings(api.ProxyUpdate request)` → `updateProxySettings({String? proxyUrl, ...})`（内部构造）
- `updateSystemSetting(api.SettingUpdate request)` → `updateSystemSetting(String key, String value)`（内部构造）—— 注意 Provider L538 已是这样调用，只需让 Service 接受原子参数
- 同理处理 `api.SSLUpdate/UpgradeRequest/MenuUpdate/AppStoreConfigUpdate/TerminalUpdate` 等全部透出 DTO 的方法（共 ~12 处）
- `settings_provider.dart` 删除 `import '../../api/v2/setting_v2.dart' as api;`，删除所有 `api.Xxx()` 构造调用
- 同步 `menu_settings_provider.dart` 的 2 处引用
- 验证：`grep -rn "api\." lib/features/settings/settings_provider.dart` 返回空；`flutter test test/features/settings/`

### ③ Websites 1000 LOC 合规违规 + 孤儿清理

**问题**：`website_ssl_accounts_actions_part.dart` **1105 LOC** 超 1000 硬上限；`website_create_provider.dart` 34 LOC 孤儿无调用方。

**做法**：
- 将 DNS 模板表 + 校验逻辑从 `_actions_part.dart` 抽成独立 module（参照已有的真 seam 范本 `website_routing_rules_*_actions.dart`，用 import + class 而非 part）：`lib/features/websites/pages/website_dns_template_form.dart`
- 拆分后 `_actions_part.dart` 降到 800 LOC 以下（消除合规违规）
- **不**引入 `WebsiteDetailStore` 单一事实源（那是 3-Provider 共享重构，blast radius 更大，本轮只做合规违规修复，留 TODO 注释指向架构评审记录）
- 删除孤儿 `lib/features/websites/providers/website_create_provider.dart`（先 grep 确认零引用）
- 验证：`wc -l` 确认无超 1000 文件；`grep -rn WebsiteCreateProvider` 返回空；websites 测试全绿

### ④ ModuleRegistry — 收敛 4-5 处 switch

**问题**：新增模块需改 `module_page_factory.dart`(switch 8 cases) + `shell_navigation.dart`(switch 路由映射) + `app_router.dart`(RouteEntry 注册) + `app_shell_page.dart`(_openStandaloneModule switch)。`RouteRegistry` seam 已存在但 module 侧未走完。

**做法**：引入 `ModuleRegistry` seam，每个模块自包含注册。
- 新建 `lib/features/shell/module_registry.dart`：
  ```
  class ModuleRegistration {
    final ClientModule module;
    final WidgetBuilder builder;        // 替代 module_page_factory switch
    final Map<String, bool> routePinning; // route → embedInShell，替代 shell_navigation switch
  }
  class ModuleRegistry { static final Map<ClientModule, ModuleRegistration> _entries; ... }
  ```
- `module_page_factory.dart` 的 switch 改为查 `ModuleRegistry`，serverId null 检查保留为统一 guard
- `shell_navigation.dart` 的 `shellRouteTargetForRoute` 改为遍历注册表
- 各模块新建 `*_module_registration.dart`（或并入现有 page 文件）自注册
- 验证：新增一个 dummy module 只改 1 处即可注册（写测试证明）；现有 33 模块路由行为不变

### ⑤ 平台通道合规修复

**问题**：`transfer_manager_provider.dart:79` 裸 `MethodChannel('onepanel/ohos_download')`（违反 AGENTS.md）；channel 名 `'onepanel/ohos_download'` 散落 3 处（provider + ohos_platform_channel + 隐式）。

**做法**：
- `OhosDownloadService` 新增默认工厂构造：`OhosDownloadService.defaultChannels(PlatformFileService fileService)` 内部用常量构造 channel
- 新建 channel 名常量源 `lib/core/platform/services/ohos_channel_names.dart`：`static const ohosDownloadChannel = 'onepanel/ohos_download';` 等
- `ohos_platform_channel.dart` 和 `transfer_manager_provider.dart` 改引用常量
- `transfer_manager_provider.dart` 改用 `OhosDownloadService.defaultChannels(...)`，消除裸 MethodChannel
- 验证：`grep -rn "MethodChannel('onepanel" lib/features/` 返回空；channel 名 grep 只命中常量源 1 处

### ⑥ 反馈规范统一

**问题**：11 文件含 `ScaffoldMessenger`（toolbox×5、apps×3、server×2、files×1）；`server_list_view_model.dart:213` 在 State 层取 `ScaffoldMessenger`（seam 方向倒置）；`settings_provider.dart:148` raw error 未经 `ErrorMessageUtils`。

**做法**：
- 11 处 `ScaffoldMessenger.showSnackBar` 迁移到 `SnackBarUtils.showSuccess/showError/...`
- `server_list_view_model.dart`：移除 `ScaffoldMessenger.of(context)`，改为暴露语义化状态（`MountResult` enum / `OperationResult`），由 UI 层 watch 后调 SnackBarUtils
- `settings_provider.dart:148`：`'$action失败: $error'` 改为经 `ErrorMessageUtils.format(error)` 加工
- 验证：`grep -rln "ScaffoldMessenger" lib/features/ lib/pages/` 仅剩 SnackBarUtils 内部 1 处；server_list_view_model 无 ScaffoldMessenger 引用
